# 发送端 PWM、同步采样与 UDP 实现说明

工程：finalboardTX。日期：2026-10-27。当前路径：屏幕确认频率 → 三路独立 PWM；两路 ADC + 三路实际 PWM 引脚采样 → 打包 → 单向 UDP。

## 已实现的行为

- D1：PA15 / TIM2_CH1；D2：PH6 / TIM12_CH1；D3：PB4 / TIM3_CH1。
- 屏幕点“确认”才改变当前通道的实际 PWM，编辑草稿不会改变输出。三路初值均为 1000 Hz，范围 100–10000 Hz，固定约 50% 占空比。
- 三个定时器各自使用约 1 MHz 计数时钟，改变 ARR/CCR1 实现独立调频。频率按整数周期取整，`pwm_diag.actual_millihz` 记录定时器实际实现的频率。奇数周期计数时，占空比略低于 50%。
- 两路模拟信号使用 ADC3 的 IN0（PA0）和 IN8（PF10），按此顺序扫描；每 2 μs 触发一组，即每通道 500 kS/s。
- 三路数字信号来自 PA15/PH6/PB4 的实际 GPIO 输入数据寄存器，按相同节拍用 DMA 读取，并非按设置频率合成的理想波形。
- 网络目标为 192.168.10.2:5000，发送端为 192.168.10.1，UDP 本地源端口为 5001。接收端不需要回传时基命令。
- 网络断开、ARP 未完成或发送积压时，采样继续，过旧数据被丢弃并累计计数。UDP 不重传，接收端根据序号和样本位置识别缺口。

## TIM4 和 TIM8 怎样同步采样

保留 TIM4 作为 2 μs 采样主时钟。TIM4 TRGO 一方面触发 ADC3，另一方面通过内部 ITR2 复位 TIM8。TIM8 每次被复位产生一次更新事件，将 CH1/CH2/CH3 的 DMA 请求送到 DMA2 Stream2/3/4。ADC3 使用 DMA2 Stream0，不与数字采样占用同一个 Stream。TIM8 本身不输出额外引脚波形，也没有 500 kHz 的软件采样中断。

TIM8 的自然溢出周期长于 2 μs，因此正常工作时其更新仅由 TIM4 的同步复位产生。三个未使用的比较值设为 65535，避开计数器复位为 0 的时刻。完成中断还核对 GPIO DMA 的当前位置，若明显错位则换会话并重新同步，避免发送错位数据。

三路 GPIO 的读取仍有内部同步和 DMA 仲裁延迟，不能理解为五路信号在完全相同的纳秒被锁存。两路 ADC 为顺序转换，IN8 采样比 IN0 晚约 600 ns（ADC 时钟 25 MHz、3 周期采样、12 位转换）；协议携带该偏移。

F746 存在定时器触发 ADC 的芯片勘误。最终使用 ST ES0290 §2.2.1 对 TIM4 TRGO 的规避措施：开启 DAC 外设时钟，以恢复内部触发路径；本工程未启动 DAC 输出。ADC 保持上升沿触发，DMA 启用 FIFO。开发中测试过 TIM8 TRGO 等方案，最终代码以 TIM4 主时钟方案为准。

参考：[RM0385，DMA2 请求映射表 26](https://www.st.com/resource/en/reference_manual/dm00124865.pdf)、[ES0290，定时器 ADC 触发勘误](https://www.st.com/resource/en/errata_sheet/es0290-stm32f74xxx-and-stm32f75xxx-device-limitations-stmicroelectronics.pdf)。

## 缓冲区怎样工作

ADC 原始缓冲严格为 8192 字节：4096 个 uint16_t，存 2048 组 IN0/IN8 数据；前后两个半区各 4096 字节、1024 组，分别约每 2.048 ms 完成一次。

另外三块数字 DMA 缓冲各 2048 字节，分别保存 GPIOA 高字节、GPIOH 低字节、GPIOB 低字节。它们与 ADC 原始环形缓冲覆盖相同的 2048 个采样时刻。**8 KiB 是 ADC 缓冲大小，不是整个采集和网络系统的总内存。**

```text
TIM4 每 2 μs 更新
  ├─ ADC3 顺序转换 IN0、IN8 → 8 KiB 循环 DMA
  ├─ 同步复位 TIM8 → DMA2 Stream2 → PA15 所在的 GPIOA 高字节
  ├─ DMA2 Stream3 → PH6 所在的 GPIOH 低字节
  └─ DMA2 Stream4 → PB4 所在的 GPIOB 低字节
             ↓ ADC 半满/全满中断，只发布“哪个半区完成”
  SamplePack 任务 → 1024 个 32 位混合记录 → 8 块发送队列
             ↓
  SampleUDP 任务 → 每块拆成 4 个 UDP 包 → 192.168.10.2:5000
```

打包任务会在读取前后检查该 DMA 半区是否仍然有效，已被 DMA 再次使用的数据直接丢弃，不当作正常数据发送。发送队列只有 8 块，约对应 16.384 ms 数据，不能无限吸收接收端或网络的停顿。

## 每条采样记录与包头

每个样本组打包为小端 uint32_t：

| 位 | 内容 |
| --- | --- |
| 0–11 | ADC3 IN0 原始 12 位值 |
| 12–23 | ADC3 IN8 原始 12 位值 |
| 24 | D1 / PA15 实测电平 |
| 25 | D2 / PH6 实测电平 |
| 26 | D3 / PB4 实测电平 |
| 27–31 | 保留，固定 0 |

每包为 48 字节包头 + 256×4 字节采样记录，总 UDP 载荷 1072 字节，不需要 IP 分片。

| 字节偏移 | 类型 | 内容 |
| --- | --- | --- |
| 0 | 4 字节 | 魔数 TXS1 |
| 4 | uint8 | 版本 1 |
| 5 | uint8 | 包头长度 48 |
| 6 | uint16 | 样本组数 256 |
| 8 | uint32 | 数据流会话号；重启采样后变化 |
| 12 | uint32 | 包序号：块序号×4+包内片号 |
| 16 | uint64 | 此包首个样本组的位置 |
| 24 | uint32 | 标称采样周期，2000 ns |
| 28/32/36 | 三个 uint32 | 此块完成时的 D1/D2/D3 设置频率 |
| 40 | uint32 | DMA 块序号 |
| 44 | uint16 | 标志：位 0 表示实际 GPIO 采样，位 1 表示 ADC 顺序扫描 |
| 46 | uint16 | ADC 两路采样时刻偏移，600 ns |

所有多字节字段均为小端。包头中的设置频率用于说明当前状态；如果频率恰好在一个块中途变化，以每条记录中的实际数字电平为准。

原始样本数据约 16 Mbit/s，包含本协议头的 UDP 载荷约 16.75 Mbit/s；加上普通以太网/IP/UDP 开销的链路需求估算约 17.8 Mbit/s。这些是设计计算，不是有线实测吞吐。

## 内存与系统配置改动

`STM32F746xx_FLASH.ld` 将 CPU 通用 RAM、采样/发送缓存、LwIP 堆和以太网描述符明确分开：

| 区域 | 地址范围/容量 | 用途 |
| --- | --- | --- |
| RAM | 0x20000000 起，128 KiB | 普通全局变量、RTOS 动态堆、主栈；包含 64 KiB DTCM 和一部分 SRAM1 |
| RAM_DMA | 0x20020000 起，128 KiB | ADC/数字 DMA、8 块打包队列、静态任务栈、RX 内存池与绘图小缓冲 |
| LWIP_HEAP | 0x20040000 起，48 KiB 保留区 | 实际 LwIP MEM_SIZE 为 32 KiB，剩余空间容纳管理开销并防止主栈重叠 |
| ETH_DESC | 0x2004C000 起，4 KiB | 32 字节对齐的 RX/TX 描述符 |

原主栈顶部为 0x20050000、栈预留起点为 0x2004C000，而 LwIP 固定堆原来从 0x20048000 开始，二者存在地址冲突风险。现将主栈顶部改为 0x20020000，网络内存单独保留。

F746 的 DMA 可以通过 AHBS 访问 DTCM，不能套用部分 STM32H7 的限制。这里搬迁网络缓冲的理由是明确划分空间、消除固定堆与栈重叠及统一对齐，而非宣称 F746 所有 DMA 都不能访问 DTCM。当前 D-cache 仍未开启。

ADC 连续 DMA 请求已启用；DMA2 Stream0 和 ADC 错误中断优先级为 5，以合法调用 FreeRTOS 的 FromISR API。CubeMX `.ioc` 中同步记录了 ADC 触发源、上升沿、连续 DMA 和相关中断配置；TIM8 的三个 GPIO DMA Stream 由独立模块在运行时管理。

## 新增函数速查

| 函数 | 用途 |
| --- | --- |
| `SenderPwm_Init()` | 启动三路独立的 1 kHz PWM |
| `SenderPwm_SetFrequency()` | 将一次已确认的屏幕参数转换为 PSC/ARR/CCR1 |
| `TimerClock()` | 根据 APB1 分频与 TIMPRE 计算实际定时器时钟 |
| `SenderStream_Start()` | 创建静态采集任务、网络任务及完成队列，启动采样 |
| `StartSamplingHardware()` | 配置 TIM4 主时钟、TIM8 同步、ADC3、GPIO DMA 和调试暂停保护 |
| `InitGpioDma()` | 配置并启动单路 GPIO 字节 DMA |
| `PublishHalf()` | 在中断中发布完成半区，不在中断中发网络包 |
| `HAL_ADC_ConvHalfCpltCallback()` | 发布 ADC 前半缓冲完成 |
| `HAL_ADC_ConvCpltCallback()` | 发布 ADC 后半缓冲完成 |
| `HAL_ADC_ErrorCallback()` | 记录 ADC 故障并停止触发，通知任务恢复 |
| `RecoverSampling()` | 停止并重新对齐四路 DMA，递增会话号标记数据中断 |
| `CaptureTask()` | 校验半区有效性，把五路数据嵌合成 32 位记录 |
| `NetworkTask()` | 检查网线/ARP、分包并通过线程安全 Netconn API 发送 |
| `SenderProtocol_Record()` | 将两个 12 位 ADC 值和三位数字电平打包 |

新增函数均在源码中附有简短用途注释。屏幕与 PWM 的连接位于 `frequencyView::confirmInput()`，仅在参数校验保存成功后调用硬件调频。

## 接线后怎样验证网络

当前没有连接网线，所以尚未做线上收包、丢包率、持续吞吐或双板联合验证。`udp_ok` 表示 LwIP 接受发送请求，不等于对端收到。

可先用电脑验收：

1. 发送板 RJ45 连接电脑有线网卡，把该网卡设置为 192.168.10.2/24。
2. 在电脑执行 `python tools/receive_samples.py --seconds 20 --output capture.txs`，根据 Windows 提示允许该接收程序访问专用网络。
3. 看接收速率是否接近 500000 组/秒、缺包是否持续增长，并检查板上 `stream_diag.udp_errors`、`ring_drops`、`overwritten_blocks`。
4. 接显示板时，显示板使用 192.168.10.2 并按本协议接收。当前没有修改显示板工程，也不能把显示板原有 C++ 数据结构直接当作该 UDP 包接收。

电脑收包工具只监听，不回传时基或控制包，也不会自动改变电脑网络设置。ARP 协议交互属于基础以太网寻址，应用采样数据仍为单向传输。

## 验证证据与边界

编译日志、写入校验日志、协议测试数据和实板采样快照保存在 `debug_evidence/`。`tests/protocol_test.c` 用已知 ADC/数字值生成包，再由 Python 独立解码检查 256 条记录及包头；这验证格式，不代替有线通信验收。

调试暂停会人为影响实时采样，因此设置了采样和 PWM 定时器的 SWD 冻结位。若仍产生 ADC 溢出，自动重新同步 DMA 并换会话号，接收端必须把会话变化视为时间轴中断，不能跨过去画一条连续波形。

恢复正常持续采样后，不需要等待网络接收，也不需要显示端发时基命令。显示端未来需持续接收、缓存并按时基选择/滤波抽取；不能只在屏幕刷新时才读取网络。

修改前源码和固件备份在项目同级 `_tx_stream_backup_20261027/`。以后重新生成 CubeMX 或 Designer 后，保留 `main.c` USER CODE 区中的 PWM/采样启动调用、顶层 CMake 中三个新模块、链接脚本中的内存分区以及 `lwipopts.h`/`ethernetif.c` 的 USER CODE 内容。


## 本次收尾结果（2026-10-27）

- PWM：用户通过屏幕设置 1000 / 2500 / 5000 Hz 后，实板寄存器及 `pwm_diag`、`frequency_ui_diag` 均读回对应值。默认 1 kHz 的真实数字采样中观察到相应边沿。此次没有使用外部示波器；三路不同频率的最终引脚波形未完成独立测量，不把寄存器核验称为外部仪器实测。
- 采样：电脑独立计时约 5.094 秒，完成 2485 个 DMA 半缓冲，换算约 499537 组/秒，符合 500 kS/s 的标称节拍；该读数受工具连接耗时和 1024 组计数量化影响。实测 DMA 回调间隔约 409600 个 CPU 周期（2.048 ms）。
- 最新快照：已打包 14121 块、14459904 组；采集队列丢失、旧半区覆盖、发送环形队列溢出、GPIO DMA 硬件错误和 GPIO 同步错位计数均为 0。无网线时这些块按设计丢弃于发送侧，不代表已经通过网络送达。
- 已知问题：运行过程中仍出现偶发 ADC OVR（最后记录 6 次，错误码 2），均已自动恢复并更换会话号。用户明确接受当前结果并要求结束对该问题的追查。因此当前不能宣称全程无采样缺口。接收端必须处理会话变化和序号缺口。
- 网络：Netconn 发送端已创建，ARP 检查与 UDP 分包逻辑已编译进实际固件；因为没有网线，UDP 成功发送计数仍为 0，尚未验证线上接收和持续吞吐。
- 构建：最终 Flash 242788 字节；CPU 通用 RAM 使用 103688 字节，RAM_DMA 使用 76864 字节；48 KiB 的网络堆区域属于链接器保留空间，实际 LwIP 堆配置为 32 KiB。固件已烧录并通过写入校验。
- 协议测试：C 编码器与 Python 独立解码器验证通过，覆盖 256 个样本、ADC/数字位域、序号、样本位置、周期、频率元数据和错误包长度。

主要证据：`debug_evidence/tim4_wall_clock_sample_rate.json`、`adc_sync_check_hotplug.txt`、`stream_final_flash.txt`、`protocol_test_packet.bin`。较早的 TRGO 试验日志和旧的 `final_pwm_measurement.json` 属于诊断中间产物，不能用作最终三路频率测量结论。

最终运行参数在重新烧录后恢复为各 1000 Hz，屏幕确认调频即可重新设定。后续接上网线后，只需继续网络实测，无需重新设计包格式或回传时基控制。
